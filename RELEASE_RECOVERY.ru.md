# Восстановление пропущенных автоматических релизов

[English](RELEASE_RECOVERY.md)

## Проблема

Push может изменить поставляемый исполняемый файл, но CI или публикация завершатся ошибкой. Следующий push может содержать только изменения README, тестов или workflow; проверка только диапазона `github.event.before..github.sha` пропустит прежнее изменение, пока не изменится другой исполняемый файл.

## Новый режим по выбору

При **push в `main`** общий Action `runtime-changes` может запросить GitHub Releases репозитория, определить последний **опубликованный** релиз с ZIP, тег версии которого является предком текущего коммита, и сравнить помеченный тегом коммит с `github.sha` через `git diff --no-renames`.

- Если накопленная разница содержит подходящие пути исполняемых файлов, выполняются существующие проверки CI и публикации; ручной тег не нужен.
- Если таких путей нет, публикация пропускается, даже если изменились документация или workflow.
- Если опубликованного ZIP-релиза ещё не было, используется **текущий диапазон push**. Это сохраняет прежнее поведение первого релиза.
- Черновики, теги не по формату версии и релизы без ZIP игнорируются.
- Теги и файлы релизов остаются неизменяемыми; не перезаписывайте и не перемещайте их.
- Если GitHub API недоступен, опубликованный тег не найден локально или ни один опубликованный тег не является предком текущего коммита, **завершайте проверку отказом**. Иначе публикация могла бы незаметно пропуститься.
- Push только документации теперь может *повторить ранее пропущенный выпуск*, но сам по себе не создаёт релиз.

Опубликованный релиз с ZIP используется как историческая контрольная точка. Некоторые старые релизы (например RuEn 1.0.0) не имеют отдельного файла SHA-256. Новые артефакты по-прежнему проверяются существующими проверками ZIP, манифеста и SHA-256 продукта.

## Workflow потребителя

Всегда закрепляйте в workflow потребителя **SHA объединённого коммита платформы**. Новый режим намеренно включается отдельно, сохраняя старое поведение для непереведённых проектов.

```yaml
- name: Detect previously unpublished runtime changes
  uses: 4FusionLab/.github/.github/actions/runtime-changes@<REVIEWED_PLATFORM_SHA>
  with:
    before: ${{ github.event.before }}
    after: ${{ github.sha }}
    paths-file: .github/release-paths.txt
    recover-unpublished: 'true'
    token: ${{ github.token }}
```

Для задания классификации используйте `permissions: contents: read`, а для checkout — `fetch-depth: 0`; `contents: write` оставляйте только заданию фактической публикации.

**Критично:** workflow релиза должен запускаться на *каждый push в main*. Фильтр `push.paths` на уровне workflow блокирует восстановление при изменении только документации даже при корректной классификации. По возможности сохраняйте узкие фильтры PR, но удалите фильтры путей push в переведённом workflow релиза.

## Проверки

- Тесты платформы охватывают пагинацию и ошибки авторизации GitHub API, вредоносные теги, проверку предков опубликованных релизов, черновики, случай отсутствия релизов и повтор пропущенного выпуска.
- CI PR продукта продолжает проверять полную сборку до релиза.
- После объединения проверяйте оба результата: `Release eligible: true` (есть неопубликованные исполняемые изменения) и `Release eligible: false` (неопубликованных входных файлов нет).
- Никогда не создавайте теги и релизы из PR или вручную запущенного workflow.
